Compose-native deployment

Deploy the whole stack, not one container.

Most platforms hand you a single image per deployment. Real applications are stacks — an API, a worker, a broker, a database. Navarch treats the entire Compose stack as the deployable unit, with versioned revisions and zero-downtime blue/green rollouts across all of it.

The core idea

Blue/green changes how many copies run. Some services must not be duplicated.

Running two copies of a stack is fine for an API. It is catastrophic for a database, and quietly wrong for a scheduler, a cron runner, or a broker holding your locks. So every service declares which it is — Navarch never guesses, because the author who does not realise blue/green changes cardinality is exactly the one an optional field fails to protect.

Swappable rollout: swap

Duplicated blue/green. The new revision comes up alongside the old, passes its health check, takes traffic, and only then does the old one go away.

blue
api · worker  rev 11
green
api · worker  rev 12

Pinned rollout: pin

Runs once, shared across revisions. Databases, brokers, schedulers — anything whose correctness assumes a single instance, whether or not it writes to disk.

shared
db  one instance, both revisions
shared
cache  one keyspace, one lock
compose.yaml
services:
  api:
    image: ghcr.io/acme/api:1.4.0
    x-composectl:
      rollout: swap        # duplicated during a rollout
      ingress: { port: 8080 }

  cache:
    image: redis:7-alpine
    command: ["redis-server", "--save", "", "--appendonly", "no"]
    x-composectl:
      rollout: pin         # mounts nothing — and still must not be duplicated

# Omitting rollout: is a parse error. There is no default, on purpose.

What you get

A platform that tells you the truth about what it did.

Every rollout is a new immutable revision. Nothing is mutated in place, so the history of what ran, when, and why it stopped is still there when you need it at three in the morning.

Append-only revisions

Rollback promotes an older revision as a new one. Deployment history is never rewritten, so it can always be read back.

Health-gated promotion

Traffic moves only after the new revision reports healthy. A bad image fails the rollout and leaves the live one untouched.

Secrets it cannot read

Values are sealed to each node's public key. Plaintext never reaches the control plane or its database — the agent decrypts at container start.

Preview environments

One call creates an ephemeral environment with a generated hostname and inherited secrets. A TTL reaps it — containers, volumes and all.

Multi-node fleet

Scored placement across real nodes. An environment is bound to the node holding its durable state and never silently moves off it.

Logs that are never stored

Container output is fetched on demand and buffered in memory. Application logs carry secrets, so none of it is written to disk.

How it works

Push a compose file. Watch it become a revision.

The control plane owns placement and writes desired state. Each node runs a dumb reconciler that converges to it — no cross-node overlay, no shared network, no orchestration cleverness to debug at midnight.

Push

Your compose file is parsed once and normalised into a versioned spec with a stable digest.

Validate

Every unsupported directive is rejected loudly, all in one pass, so you fix everything at once.

Place

The scheduler scores the fleet and writes the desired containers for one node.

Reconcile

That node's agent brings the revision up against its own Docker daemon and reports health.

Promote

Healthy revisions go live in one transaction; the router flips and the old revision is torn down.

The contract

Rejected loudly, never silently dropped.

A stack must never run differently than its author expects. If Navarch cannot honour something in your compose file, it says so at push time instead of quietly changing the meaning of your deployment.

Host port bindingsThey collide between revisions. Declare an ingress instead and the platform routes to it.
Bind mountsA host path is not portable across nodes. Named volumes are created and tracked explicitly.
privileged, cap_add, devicesThey break isolation between tenants on the same machine.
build:The platform does not build. Pre-build and push an image, so what ran is what you can reproduce.
swap on a writable volumeTwo revisions writing one filesystem is the failure classification exists to prevent. Refused outright.
A volume nobody mountsAlmost always a typo, and a typo in storage is expensive to discover later.

Terminal-first, and honest about what it doesn't do.

No automatic failover. No durable log storage. No cross-node overlay. Each of those is a deliberate position with a reason behind it, written down — not a gap you find in production.
